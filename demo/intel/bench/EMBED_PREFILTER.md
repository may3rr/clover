# 向量预选方案（T6，只写方案，不改代码）

## 现状

`backend/citecheck/support/sources.py::_bm25_excerpt` 是支持度检索的唯一入口：

1. 把被引文献全文切成句子，构造 3 句滑窗（步长 1），一篇 6000 句的论文约 6000 个窗口。
2. 对所有窗口算 BM25（`BM25Okapi`）。
3. `_dense_scores()` 对**所有窗口**调用 `llm.embed.embed(windows)`，再对查询算一个向量，得到余弦相似度。
4. BM25 与向量分数用 RRF 融合，再对前 `[llm.rerank].candidates`（默认 40）做 cross-encoder 重排。
5. 按分数取不重叠的窗口拼 excerpt（最多 5 段、2500 字符）。

成本点在第 3 步：**每个（论断，被引文献）对都要把该文献的全部窗口过一遍向量模型**。同一篇被引文献被 3 条论断引用，就要算 3 遍；一篇 55 条参考文献的稿件，窗口总量是数万到数十万级。

## 方案

在 `_bm25_excerpt` 里把「先 BM25 全量、再全量向量」改成「先 BM25、只给候选算向量」：

```text
sents -> windows
bm25_scores = BM25(windows, claim)
cand = top-K(bm25_scores)                  # K 默认 128
cand += neighbours(cand, radius=1)         # 可选：前后各 1 个窗口，补回跨句证据
dense = embed([windows[i] for i in cand])
full = zeros(len(windows)); full[cand] = dense
fused = RRF(bm25_scores, full)
rerank(top 40 of fused)
```

- K 建议 128（可配置 `[llm.embedding].prefilter_k`，0 表示关闭）。
- 邻居扩展半径 1 把候选从 128 扩到约 384 个窗口（3 句窗口彼此重叠，实际去重后更少），用来补「关键句在 BM25 第 129 名」和跨句证据。
- 重排的 40 个候选仍从融合后的 top 40 取，行为不变。

## 预计收益

以一篇 6000 窗口的文献、被 3 条论断引用为例：

| 方案 | 向量窗口数 | 相对现状 |
| --- | ---: | ---: |
| 现状（全量） | 18,000 | 100% |
| K=128 + 邻居 ±1 | 约 1,150 | 6.4% |
| K=128 无邻居 | 384 | 2.1% |
| K=64 + 邻居 ±1 | 约 580 | 3.2% |

在 NPU 上 batch=1 实测 24 窗口/1.55 s（约 0.065 s/窗口），6000 窗口约 390 s；预选到 128 后约 8 s，单篇的向量时间从分钟级降到秒级。GPU/CPU 同样受益，且 GPU 还要留给 8B judge 批处理。

## 召回影响与验证

- 现有 item bench 的历史数字：BM25 单独把关键段落放进 2500 字符 excerpt 的比例 0.38，BM25+向量融合 0.49。预选后丢失的是「BM25 排名在 K 之外、但向量能救回来」的样本。
- 风险最大的是改写/同义表述（论断用词与原文差异大）和中文长句；`_tokenize` 对中文按字符/词混合，BM25 的中文召回本来就弱。
- 建议上线前用 `demo/testset/item_bench` 或 T3 的 508 对做一次离线对照：
  - 对每一对，记录关键段落是否在 BM25 top-K、邻居扩展后是否在、融合后是否在；
  - 目标：K=128 + 邻居时，关键段落覆盖率不低于现状的 95%；
  - 若不达标，先把 K 提到 256，再考虑「BM25 top-64 ∪ 向量 top-64」的两路候选。
- 另一个保守选项：只对长文档启用预选（窗口数 > 2000），短文档保持全量；演示稿的两篇都属于长文档，收益最大。

## 配置与回退

- `[llm.embedding] prefilter_k = 128`、`prefilter_neighbors = 1`，默认 0/0 保持现状。
- 预选只影响 `_dense_scores` 的输入集合，不改变 BM25 分数、RRF、rerank 和 excerpt 拼接逻辑；关闭开关即可完全回退。
- 需要在 `demo/intel/bench/` 留一份离线对照脚本和数字（本轮未实现）。

## 与 T4 的关系

T4 的日志会给出每篇稿件的真实窗口数、embedding 调用次数与各层耗时；拿到后把上表的 6000 换成实测值，并确认向量是否是端到端的主要瓶颈。如果 T4 显示向量只占很小一部分，预选的优先级可以降低。
